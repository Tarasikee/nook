## Caveats that affect behavior

- **Hint stack semantics changed.** Chrome 133–150 and Firefox 149–152 are recorded as partial implementations of an older specification. Current semantics start at Chrome 151 and Firefox 153; Safari is still preview-only in this record. A successful hint-value check does not prove the current nesting rules. See [hint data](https://github.com/mdn/browser-compat-data/blob/a2d2a599a78df7885f57bfe21880d21821036dc5/html/global_attributes.json).
- **iOS has a separate dismissal caveat.** Although base support began in Safari 17, BCD records broken outside-tap dismissal on iOS/iPadOS before 18.3. Do not infer mobile behavior from the desktop column. See [HTMLElement.popover data](https://github.com/mdn/browser-compat-data/blob/a2d2a599a78df7885f57bfe21880d21821036dc5/api/HTMLElement.json).
- **Source option support was initially incomplete.** Chrome 133–136, Firefox 141–143, and Safari from 18.4 until before 26 lacked the focus-navigation change; fixed versions are shown first in the table. Implicit anchoring has its own row and can arrive later. See [method data](https://github.com/mdn/browser-compat-data/blob/a2d2a599a78df7885f57bfe21880d21821036dc5/api/HTMLElement.json).
- **Interest invokers remain a separate experimental capability.** BCD marks the HTML/DOM surfaces experimental and not on the standard track. The presence of a guide or Chromium implementation is not evidence of cross-browser support. See [button data](https://github.com/mdn/browser-compat-data/blob/a2d2a599a78df7885f57bfe21880d21821036dc5/html/elements/button.json).
- **CSS transition pieces do not ship together.** Support for starting styles and discrete transitions does not imply support for retaining top-layer rendering with overlay. See the individual CSS rows.
- **Positioning has subfeature differences.** The older Chromium name was inset-area. BCD also notes a Chromium issue when position-area has no matching anchor, and version differences for some logical keywords. The table is not a complete CSS-anchor support matrix. See [position-area data](https://github.com/mdn/browser-compat-data/blob/a2d2a599a78df7885f57bfe21880d21821036dc5/css/properties/position-area.json).

The selected records use BCD mirror entries for Edge and most Android counterparts. This table does not resolve every browser mapping or WebView release; consult the dataset for those targets. The iOS exception above is explicitly recorded rather than mirrored.

## Detection and validation plan

These are future implementation checks, not utilities added to the repository.

| Need | Check to investigate | Limitation |
| --- | --- | --- |
| Basic Popover API | Presence of HTMLElement.popover and required methods | Says nothing about newer modes/options |
| Hint mode | Set hint on a detached element and inspect the reflected popover value | Does not prove corrected stack semantics |
| Interest invokers | Presence of interestForElement on the actual invoker interface | Test the full interaction and related CSS separately |
| CSS positioning / timing | CSS.supports for the exact property/value and selector used | Parsing support does not verify placement or behavior |
| Source option / event source | Check event-property availability and exercise invoker focus/anchor behavior | Method existence and ignored options can give false confidence |
| Browser baseline | Real interaction tests in target versions, including mobile | BCD is evidence, not a substitute for those tests |

Nook currently prioritizes its main native features and accepts limited browser availability. Record required capabilities and support gaps per feature. Compatibility fixes, polyfills, and fallback implementations are deferred for now; this matrix documents limitations rather than gating development on broad browser support.

## Current Nook mapping

As of this snapshot, `createPopover()` requires the base Popover API and a supported button or button-type input invoker. It uses the declarative `popovertarget` relationship, then passes the trigger as `source` when controller methods show or toggle the element. Browsers that support base popovers but have incomplete `source` support can still expose a popover, while newer focus-navigation and anchoring refinements are not guaranteed.

`createTooltip()` uses Nook-managed pointer and focus listeners to request a `popover="hint"` surface. It does not yet use interest invokers. The current hint stack behavior therefore needs the versions recorded in the hint row; older or unsupported browsers can interpret the unknown `hint` value as a manual popover. Nook deliberately supplies no fallback, polyfill, or compatibility layer for that case.
