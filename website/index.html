Current API

Small enough to read in one pass.

The first APIs are intentionally narrow while the public package shape is being proven in real interfaces.

createPopovercreateTooltipPopoverController

createPopover(options)

Connects a button or button-like input to a content element using the native declarative invoker relationship.

trigger
A button or button-type input. Its own click handler remains intact.
content
An element with an id. Nook sets its popover attribute and references that id from the trigger.
mode
'auto' by default; use 'manual' for application-controlled visibility or 'hint' where its newer platform behavior is required.
onToggle
Receives the actual open state after the browser completes a transition.

createTooltip(options)

Shows a hint popover after pointer interest or keyboard focus. It uses listeners installed with an abortable lifecycle and never assigns to onclick, onfocus, or other consumer properties.

openDelay
Milliseconds before showing. Defaults to 400.
closeDelay
Milliseconds before hiding. Defaults to 80.

PopoverController

Both functions return show(), hide(), toggle(), isOpen(), and destroy(). Call destroy() when the elements leave your application lifecycle; it removes Nook listeners and restores attributes it changed.

What this means today

Popover needs the base Popover API. Tooltip currently relies on the newer hint mode; browsers that do not recognize it can treat it as manual, so it does not preserve the native hint stack behavior.

Nook intentionally has no fallback or polyfill at this stage. Interest invokers are tracked as a promising future browser primitive, but Nook does not use them yet.

Implementation notes

Native relationships solve the common collision.

Floating-element libraries often need to compose several trigger props so hover, focus, click, and consumer handlers can cooperate. Nook starts with a different question: can the actual element and browser relationship express this interaction?

For a click popover, popovertarget provides that relationship. For behavior that still needs JavaScript, Nook observes with separate event listeners rather than overwriting an application handler. This keeps event ownership visible and lets an auto popover and a hint coexist where the browser supports those modes.

Native popovers render in the top layer, so they are not clipped by ancestor overflow or ordinary stacking contexts. Positioning, semantic roles, keyboard models, and focus requirements still belong to the specific component you build on top.
